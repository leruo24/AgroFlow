# Machine learning evaluation: 24-hour soil moisture forecast

This records what was measured for the forecast model behind the zone screen's
"Forecast (machine learning model)" line. The numbers come from
`backend/AgroFlow.Api/Ml/moisture-model-evaluation.json`, written by the training run on
14 October 2026. Nothing here is estimated.

**Summary.** On the held-out simulated data the plain FAO-56 water balance predicts tomorrow's
moisture better than the machine learning model. That is expected, because the simulated
readings are generated by that same water balance. The model has **not** been tested on real
sensor readings: none were available for this run. So it does not, and cannot yet, claim to
be more accurate than the FAO-56 engine. PrimaryAction (the engine's watering decision) is
unchanged and does not use the model.

## What the model predicts

Soil moisture (relative %, 0 = wilting point, 100 = field capacity) 24 hours ahead, for a day
with no watering. The model is ML.NET `FastTree` regression (Microsoft.ML 4.0.3, in-process, seed
20261014) with these inputs:

| Input | Meaning |
| --- | --- |
| Current moisture | Relative % now |
| Hours since irrigation | Whole days since the last logged watering × 24, capped at 720 ("none in 30 days") |
| Temperature max / min | Today's weather (°C) |
| Humidity | Today's mean relative humidity (%) |
| Forecast rain | Rain for the next 24 hours (mm) |
| Reference ET | ETo for the next 24 hours from the existing engine (`DailyEtoResolver` via `Fao56Engine`) |
| Soil type | Sandy / loam / clay (one-hot) |
| Crop stage | Establishing / Growing / Peak growth / Nearing harvest / Season complete (one-hot) |

The zone screen turns the prediction into hours with a straight line from now to the 24-hour
value, until the zone reaches the engine's watering level (where depletion reaches RAW). For example,
"Likely to need water in about 14 hours". The line is hidden when there is no model, no
reading in the last 26 hours, readings on fewer than 3 of the last 7 days, or no water balance or
forecast for the zone.

## Data used

| | Examples | Simulated | Real |
| --- | ---: | ---: | ---: |
| All | 22,579 | 22,579 | **0** |
| Training (days before 30 Dec 2025) | 17,831 | 17,831 | 0 |
| Held-out test (30 Dec 2025 – 29 Sep 2026) | 4,748 | 4,748 | 0 |

**No real readings were used.** The training command tries the database for simulated and real
readings (`sensor_reading.simulated` and `farm.is_simulated` mark which is which). This run was
made with `--no-db`, because the local database password in user-secrets was rejected
(authentication failed) and was not retried. Real-sensor accuracy is therefore **not measured**.

**How the simulated examples were made.** These are the two simulated demo farms from migration 0047,
generated by the same rules as `SimulationService`:

- **Weather:** real Open-Meteo ERA5 archive weather, 1 Jan 2023 – 30 Sep 2026. The snapshots are saved in
  `backend/AgroFlow.Api/Ml/training-weather/`:
  - Rustlers Valley (Simulated): Ficksburg coordinates −28.872, 27.87506, citrus (11,755 examples);
  - Brits (Simulated): −25.63473, 27.78022, tomato (10,824 examples).
- **Soil:** the existing FAO-56 balance (`Fao56Engine.Run`, one day at a time). Moisture comes from
  `SimulationRules.MoistureFromStoredBalance`, which adds at most ±0.35 points of deterministic noise.
- **Simulation assumptions (not measurements):**
  - each farm is run on all three soils with three planting dates (0, 45 and 90 days in);
  - the crop is replanted when its season ends, after watering the soil to field capacity;
  - the farmer waters back to field capacity the day after the balance passes RAW.
- **Which days count:** a day is used only when the following day has no watering.
- **Forecast rain:** this is the next day's *observed* rain. Open-Meteo's historical-forecast API returned rain
  identical to the archive for these sites, so no genuine past forecasts were available.
  Both the model and the baseline therefore had perfect rain forecasts. Real use will be worse.

The held-out set is split by date, not at random: every test day comes after every training day.

## Results (held-out set, 4,748 examples, all simulated)

| Predictor | MAE (percentage points) | R² |
| --- | ---: | ---: |
| Machine learning model (FastTree) | **0.648** | **0.9954** |
| Baseline: FAO-56 water balance alone | **0.041** | **0.9999** |
| No change (tomorrow = today), for scale | 3.128 | 0.9121 |

Exact values: model MAE 0.6475811471593607, R² 0.995444556988062; FAO-56 baseline MAE
0.04129736230510364, R² 0.9999452310508338; no-change MAE 3.127613732097725, R² 0.9121039361729771.

The FAO-56 baseline runs the engine's own daily step (`Fao56Engine.BuildDay`: Eq. 81, 84 and 85,
with the effective-rain rule) once from today's moisture, with no watering. A test
(`Fao56_baseline_matches_one_day_of_the_engine`) checks it gives the engine's own result.

**Real-reading results: not measured** (0 real examples).

## Reading these numbers

- **The baseline's near-perfect score is not evidence that FAO-56 is perfect in the field.**
  The "truth" here *is* the FAO-56 balance plus a little noise. The noise also changes only slowly from
  one day to the next, so it barely affects a 24-hour change.
- **The model is close behind but not better.** It learned the balance's behaviour from examples, at
  0.65 points average error. It beats "no change" by a wide margin.
- **What would show whether the model adds anything:** real sensor readings, which drain, crust,
  run off and respond to watering in ways the balance does not model. Retrain with
  them (below) and compare the "real only" rows the training report adds automatically
  (`ModelOnRealOnly`, `Fao56BaselineOnRealOnly`).

## Retraining

From the repository root:

```
dotnet run --project backend/AgroFlow.Api -- train-moisture-model
```

This overwrites `backend/AgroFlow.Api/Ml/moisture-model.zip` and
`moisture-model-evaluation.json`, and adds database rows when `ConnectionStrings:Supabase`
connects.

Options:
- `--no-db`: simulated weather files only;
- `--out <path>`: write the model somewhere else;
- `--weather-dir <dir>`: read the weather snapshots from another folder.

A weekly retraining job exists in the API and is **off by default**. To turn it on, set:
- `Ml__Retrain__Enabled=true`
- `Ml__ModelPath=<writable file>`

It trains from the database only, skips the run if there are fewer than 200 examples, and
starts using the new model immediately.

## Fault checks

These run hourly and are **off by default**; set `Ml__FaultDetection__Enabled=true` to turn them on.
They raise one open in-app alert per zone and a Telegram message to every farm member. The alert
starts "Possible sensor or water supply problem — please check." and names the reason. Four checks:

- **Pump ran but moisture did not rise:** less than 2 points within 60 minutes of a run of at least 2 minutes.
- **Sensor unchanged:** the same value (±0.05) over 12 hours, from at least 4 readings.
- **ML.NET IID spike detection:** run on the change between readings. A jump must be at least 5 points.
- **ML.NET IID change-point detection:** run on the level. The newest readings must sit at least 5 points
  from the earlier level.

Jumps within 6 hours of a pump run, or on a day with at least 2 mm of rain, are ignored, and only the
3 newest readings are judged.

The unit tests check these on synthetic sequences only. Their false-alarm rate on real farms has
**not been measured**.
